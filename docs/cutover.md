# Переключение production с Redis на Postgres

Runbook для одного переключения. Выполняет человек с доступом к Vercel и Neon; каждый шаг проверяется перед следующим.
Займёт около 30 минут, из них около 15 — окно без записей.

Redis во время и после переключения **только читается**. Он остаётся точкой отката минимум на 30 дней.

## Перед началом

- [ ] В production задеплоен код со слоем репозиториев и Postgres-реализацией; `DATA_BACKEND` в Vercel не задан
      (значит, `redis`). Приложение работает как раньше.
- [ ] Настроены бэкапы (`docs/restore.md`, раздел «Настройка»). Их можно включить и после переключения:
      до него production-база пустая.
- [ ] В Vercel у Production есть `DATABASE_URL` и `DATABASE_URL_UNPOOLED` от интеграции Neon.
- [ ] Локально: Node 22, репозиторий на том же коммите, что в production, выполнен `npm ci`.
- [ ] Окно без записей согласовано с обоими пользователями на ~15 минут: никто не вносит траты, в том числе
      через Siri. Перед окном откройте приложение онлайн, чтобы офлайн-очередь отправилась.

## Подготовка окружения

```sh
vercel env pull .env.production.local --environment=production
set -a; source .env.production.local; set +a
# Хост production-базы — по нему скрипты узнают production и требуют --production
export PRODUCTION_DB_HOST="$(node -e 'console.log(new URL(process.env.DATABASE_URL_UNPOOLED).hostname)')"
echo "$PRODUCTION_DB_HOST"   # ep-…: сверьте в консоли Neon, что это production-ветка
echo "$USERS"                # первый пользователь станет owner бюджета
```

`.env.production.local` содержит production-секреты. Удалите его сразу после переключения (шаг 9). Пока файл лежит
в проекте, локальные `next build/start` тоже подключаются к production.

## Шаги

### 1. Ручной экспорт — дополнительная копия

Оба пользователя: Настройки → **Экспорт JSON**. Каждый файл содержит семейные данные и личные данные своего
владельца, поэтому полная копия — это два файла. Храните их приватно.

### 2. Схема в production-базе

```sh
npm run db:migrate -- --production
```
Ожидаемо: `Миграции применены: ep-…`. Повторный запуск безопасен.

### 3. Пробный перенос, затем настоящий

```sh
npm run db:migrate-redis -- --production --dry-run
```
Проверьте таблицу: числа трат, доходов, счетов и регулярных похожи на правду. Строки `не перенесено:` допустимы
только для ключей вне `ft:index` (их и сейчас не видно в приложении). Если скрипт отказал — читайте причину
(старый формат, суммы с 3 знаками) и не продолжайте.

```sh
npm run db:migrate-redis -- --production
```

### 4. Сверка — 0 расхождений

```sh
npm run db:verify -- --production
```
Ожидаемо: `Расхождений нет (N показателей)` и код выхода 0. Совпадать должны и строки `ответ /api/data для …`:
это значит, что каждый пользователь увидит ровно то же, что сейчас.

**Если есть расхождения — не переключайте.** Production по-прежнему работает на Redis, ничего не сломано.
Разберитесь с причиной; базу можно очистить и начать с шага 2:
```sh
psql "$DATABASE_URL_UNPOOLED" -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public; DROP SCHEMA IF EXISTS drizzle CASCADE;'
```
(только до шага 5 — после переключения в базе живые данные).

### 5. Переключение

Vercel → проект → Settings → Environment Variables → **Add**: `DATA_BACKEND` = `postgres`, только окружение
**Production**. Затем Deployments → текущий production-деплой → **⋯ → Redeploy**: новые переменные действуют
только после редеплоя.

### 6. Сверка сразу после редеплоя — до того, как кто-то начнёт пользоваться

```sh
npm run db:verify -- --production
```
- **0 расхождений** — в окне никто ничего не записал в Redis. Переходите к шагу 7.
- **Есть расхождения** — между шагами 3 и 5 кто-то записал в Redis. Повторите перенос и сверку:
  ```sh
  npm run db:migrate-redis -- --production && npm run db:verify -- --production
  ```
  Это безопасно: если в Postgres уже появились новые записи, перенос откажет («данные новее Redis») и ничего
  не перезапишет. Тогда сверьте вручную, какие записи из списка нужны.

### 7. Смоук-проверка вручную

Под **каждым** пользователем, на телефоне и на компьютере:
- [ ] Вход работает, последние траты на месте, суммы на «Лимитах» и графике те же, что до переключения
      (сравните со скриншотом или экспортом шага 1).
- [ ] Записать тестовую трату → она появилась → удалить → «Вернуть» → удалить снова.
- [ ] Сбережения: счета, копилки и история сверок на месте. Сверку проводите, только если всё равно собирались:
      снимок сверки не удаляется.
- [ ] План текущего и следующего месяца открывается, суммы прежние.
- [ ] Регулярные: список и блок «К оплате» прежние. Тестовую оплату не делайте: оплата — это настоящая трата.
- [ ] Быстрые команды: в настройках виден прежний токен. Фраза в Siri записывает трату (потом удалите её).
- [ ] Vercel → Logs (production): нет ошибок 500.

### 8. Бэкап

Actions → **Backup** → Run workflow. Убедитесь, что в репозитории бэкапов появился файл и он расшифровывается:
`age -d -i backup.key <файл> | gunzip | head`.

### 9. Уборка

```sh
rm .env.production.local
```
Redis и интеграцию Upstash в Vercel не удаляйте 30 дней. Приложение в них больше не пишет и не читает.

## Откат

Когда: ошибки 500, неверные суммы, пропавшие данные — всё, что не исправляется быстро.

1. Vercel → Environment Variables → `DATA_BACKEND` = `redis` (или удалите переменную) → **Redeploy**.
2. Приложение снова работает на Redis — **в состоянии на момент шага 5**. Postgres не меняется и не удаляется.

### Что делать с записями, сделанными в Postgres после переключения

После отката их нет в Redis. Варианты:

**A. Вручную** — если после переключения прошло мало времени и записей немного (до пары десятков трат):
перед откатом оба пользователя делают «Экспорт JSON» (приложение ещё на Postgres). После отката недостающие
траты вносятся заново по этим файлам. Новые записи легко найти: у них дата позже шага 5.

**B. Обратный перенос только новых записей** — если записей много или прошло несколько дней.
Скрипт `scripts/migrate-pg-to-redis.ts` (пока не написан, около часа работы) по той же схеме, что прямой перенос:
- читает снимок Postgres и Redis и сравнивает их по id и версиям — та же функция, что защищает прямой перенос;
- **добавляет** в Redis записи, которых там нет: траты и доходы (с регистрацией ключа месяца в `ft:index`), сверки,
  пункты плана, платежи, счета, копилки, токены, подписки;
- **обновляет** документы, у которых версия в Postgres выше: настройки, личные настройки, планы, счета, копилки,
  платежи, пункты плана;
- записи, удалённые в Postgres после переключения, **не удаляет**, а выводит списком для ручного решения;
- `--dry-run` показывает план изменений, после записи — сверка в обратную сторону (`db:verify` должен дать 0 расхождений).

Рекомендация: если откат случился в первый день — вариант A. Если позже — B. Чтобы откат не ждал разработки,
скрипт B можно написать заранее, до переключения.

### Повторное переключение после отката

Перенос не удаляет строки, а старые данные Postgres устарели. Перед повтором очистите базу командой из шага 4
(после того как новые записи перенесены в Redis по варианту A или B), затем начните с шага 2.
